# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

µWidgets — a standalone Android app (Kotlin) providing minimal home-screen widgets: a **weather widget** (current temperature + optional emoji/condition line) and an **upcoming-alarm widget** (alarm icon + next-alarm time). Styled to match µLauncher's clock — transparent background, white text with a shadow, Hack font — but it depends on nothing from µLauncher; any launcher can host the widgets. Package `com.wassupluke.widgets`.

## Build & Run

JDK 17+ (source/target 17; JDK 21 runs the build fine). Requires `local.properties` with `sdk.dir=<android-sdk-path>` (gitignored — create it locally; the build fails without it).

- Debug build / install: `./gradlew :app:assembleDebug` / `./gradlew :app:installDebug`. The debug build has `applicationIdSuffix = ".debug"` (+ `versionNameSuffix` and a debug-only `app_name` in `src/debug/res`) so it installs **alongside** a release build for on-device testing without disturbing it.
- All unit tests: `./gradlew :app:testDebugUnitTest`
- One test class: `./gradlew :app:testDebugUnitTest --tests "com.wassupluke.widgets.WeatherCodeTest"`
- Lint: `./gradlew lintDebug` (`abortOnError = true`, so lint failures break the build — CI runs this too).
- minSdk 26, compile/target 36. There is no `app:installDebug` device check — connect a device/emulator first.

**Versioning is git-derived** (`app/build.gradle.kts`): `versionCode` = `git rev-list --count HEAD`, `versionName` = `git describe --tags --always`. A build needs real git history with tags — a shallow/zero-depth checkout yields a wrong version (hence the full-depth checkout in CI).

**CI** (`.github/workflows/`): `check.yml` runs lint + unit tests on PRs/pushes to `main`; `dev-release.yml` builds, signs, and publishes a prerelease to the force-pushed `dev` tag on every push to `main`; `release.yml` does the same for `v*` tags. Release builds are signed via repo secrets (`SIGNING_KEY`/`ALIAS`/…) — there is no committed keystore.

## Architecture

There are **two widget families** sharing one Android glue layer: the weather widget (the bulk of the app, modeled as **fetch → cache → render**) and the simpler alarm widget (**read system state → render**, no network, no cache). Logic is split into a pure, unit-tested data layer and a thin Android glue layer.

### Data layer (`data/`) — pure, JVM-unit-tested
- `WeatherRepository.refresh()` orchestrates: get location → fetch → parse, returning a sealed `RefreshResult` (`Success`/`NoPermission`/`NoLocation`/`NetworkError`). It depends on two interfaces so it can be tested with fakes:
  - `LocationProvider` → `LocationResult` (`Available`/`PermissionMissing`/`Unavailable`). Production impl `FrameworkLocationProvider` uses the **framework `LocationManager` only — no Google Play Services / FusedLocation** (keeps the app FOSS-friendly). `getLocation` tries, in order: a last-known fix **only if < 2 h old**, else a single timed-out current fix (API-version-branched: `getCurrentLocation` on R+, explicit `LocationListener` on 26–29) which works in the foreground but returns nothing in the background, else a **warm-cache** fallback. **A background app is denied an on-demand location fix on this OS even with `ACCESS_BACKGROUND_LOCATION`** (a background *pull* returns nothing) — so location is kept fresh by a *push*: `BackgroundLocationUpdates` registers OS-delivered `NETWORK` updates via a mutable `PendingIntent` → `LocationUpdateReceiver`, which persists each fix to a shared `LocationCache` (`location_cache` prefs, also written by the provider on a live fix). `getLocation` reuses that cache, capped at 2 h, so the widget never shows long-stale-location weather (e.g. home weather on a weekend away). `LocationCache.isFresh` requires the age to be in `0..maxAge` — a **future** timestamp (clock change, or a fix carrying satellite time) is treated as unusable rather than eternally fresh, so the caller falls through to a live fix. `encode`/`decode` are the pure `Double`↔`Long`-bits storage helpers, split out so the encoding is JVM-unit-testable. `ACCESS_BACKGROUND_LOCATION` ("Allow all the time") is still required — the pushed updates need it.
  - `HttpClient` → production impl `UrlHttpClient` (`HttpURLConnection`).
- `OpenMeteo` builds the Open-Meteo URL (no API key) and parses the response (kotlinx.serialization). `WeatherData` is the model; `WeatherCache` persists the last result in SharedPreferences.
- `WeatherCode.describe(code)` maps WMO codes → emoji+label.
- `AlarmDay.dayPrefix(...)` computes the alarm widget's day label (null = today/past, the localized "tomorrow" word for +1 day, short weekday for 2–6 days out, else `MMM d`) — pure `java.time`, unit-tested.
- **Temperature is a display concern, not a fetch concern.** Weather is always fetched and cached in **Celsius** (`WeatherData.temperature`); the unit is applied only at render time by `formatTemperature(celsius, unit)`. So changing the unit re-renders instantly with no refetch and no stale-unit window. `TemperatureUnit.forLocale(locale)` is the best-effort "Automatic" resolver (reads Android 14+ `mu`/`ms` Unicode locale extensions, then a country fallback).

**IMPORTANT — the data layer must stay free of Android-only APIs** (e.g. `android.net.Uri`, `android.icu.*`). Its unit tests run on the plain JVM (no Robolectric), so such calls would compile but throw at test time. Hand-rolled URL building and the extension/country-based locale→unit resolution exist deliberately for this reason — the Android-side `Settings.resolvedUnit(context)` is where context/config-locale access lives.

### Android glue (package root `com/wassupluke/widgets/`)
- `WeatherWidgetProvider : AppWidgetProvider` — `renderWidgets(context)` is the single place that builds the **weather** `RemoteViews` (loads cache + `Settings`, computes the values once, then loops over widget ids). It also **owns the refresh schedule**: `onEnabled`/`onUpdate` arm an `AlarmManager.setAndAllowWhileIdle` ~30-min heartbeat (`ACTION_HEARTBEAT`), `onDisabled` cancels it, and `onReceive` re-arms on each heartbeat fire / re-arms after `BOOT_COMPLETED` (alarms are cleared by reboot). **`onUpdate` must NOT start a fetch** — the host (e.g. the launcher's `AppWidgetHost`) can fire it repeatedly, and once a fetch re-rendered the widget that re-fired `onUpdate`, producing a refresh loop. So the initial fetch lives in `onEnabled` (first widget placed); `onUpdate` only renders + ensures the heartbeat. The heartbeat (and tap/`ACTION_REFRESH`) enqueue a one-shot `RefreshWeatherWorker`.
- `AlarmWidgetProvider : AppWidgetProvider` — `renderAlarmWidgets(context)` is the single place that builds the **alarm** `RemoteViews`. It is **broadcast-driven, not WorkManager-scheduled**: `onReceive` re-renders on `ACTION_NEXT_ALARM_CLOCK_CHANGED` / time / timezone / boot. `nextUserAlarm` reads `AlarmManager.nextAlarmClock` but ignores alarms whose `showIntent` creator package has no launcher activity (filters out non-user alarms). Tap target falls back: configured app → the alarm's own `showIntent` → system `ACTION_SHOW_ALARMS`.
- `WidgetStyle` (`object`) — per-render visual styling **shared by both providers**: `textColor(context)` (the dynamic-color/wallpaper logic) and `gravity(context)` (vertical-center + the horizontal `Settings.textAlign`). Both `renderWidgets` and `renderAlarmWidgets` pull color/gravity from here — change rendering style once, in `WidgetStyle`.
- `RefreshWeatherWorker : CoroutineWorker` — the unit of **weather** fetch work (`updatePeriodMillis` is `0`; the cadence comes from the provider's heartbeat, not WorkManager periodic work, which Doze/App-Standby throttles too hard for a rarely-opened widget app). `enqueueOnce` runs an expedited one-shot with a `CONNECTED` constraint **as unique work (`REPLACE`)** so a burst of triggers (permission grant, `onResume`, heartbeat, taps, a delivered location update) coalesces into one refresh instead of re-rendering repeatedly; after a fetch it saves to cache and calls `renderWidgets`. The alarm widget has no worker.
- `BackgroundLocationUpdates` (`object`) + `LocationUpdateReceiver` — **background location by *push*, not pull.** `register`/`unregister` request OS-delivered `NETWORK` location updates (~30 min) via a mutable `PendingIntent` targeting `LocationUpdateReceiver`. This exists because a background *pull* (`getLastKnownLocation`/`getCurrentLocation`) returns nothing on this OS even with `ACCESS_BACKGROUND_LOCATION`, but pushed updates are delivered even with no live process. The receiver persists each delivered fix to `LocationCache`, enqueues a refresh, and calls `WeatherWidgetProvider.deferHeartbeat` — **both timers run at ~30 min, so without deferring they drift apart and fetch twice per interval.** Registration rules, all deliberate:
  - `register` is **idempotent** (re-requesting with the same `PendingIntent` replaces rather than stacks), so it is called on `onEnabled` / `BOOT_COMPLETED` / **every heartbeat** / `MainActivity.onResume`. The heartbeat call is the **self-heal** path: `register` no-ops when the `NETWORK` provider is disabled, and without a retry the widget would stay dead until the app was next opened.
  - It is **gated on a widget being placed** (`WeatherWidgetProvider.hasWidgets`) in `MainActivity`, which also `unregister`s when none is placed. `onDisabled` only fires on the last-widget-*removed* transition, so a user who opens the app but never places a widget would otherwise hold a 30-min location registration open forever.
  - `unregister` looks the `PendingIntent` up with `FLAG_NO_CREATE` (nothing to remove if we never registered) and `cancel()`s it.
  - Registering only needs `ACCESS_COARSE_LOCATION`, but **without `ACCESS_BACKGROUND_LOCATION` the OS delivers the updates only while the app is visible** — that case is logged as a warning rather than silently degrading.
  - **Never log coordinates outside `BuildConfig.DEBUG`** (logcat ends up in bug reports). `buildConfig = true` is enabled for exactly this; verified folded out of the release DEX.
- `MainActivity` — the app's only screen: requests `ACCESS_COARSE_LOCATION`, then (once foreground is granted, API 29+) prompts **once** for `ACCESS_BACKGROUND_LOCATION` ("Allow all the time") via `ensureBackgroundLocation` (guarded by a `Settings` flag so it never nags). `onResume` does a foreground fetch — refreshing on open and **seeding the saved location** that background refreshes reuse — and **(re)registers background location updates** (`BackgroundLocationUpdates`) so the location cache stays warm between opens, but only while a weather widget is placed (it unregisters otherwise; see above). It hosts the settings UI (show-condition toggle, temperature-unit selector, wallpaper-color toggle, font-size `SeekBar`, text-alignment `MaterialButtonToggleGroup`, and **two** tap-action pickers — one for the weather widget, one for the alarm widget — each refresh/launch-app chosen via an `AlertDialog` over `queryIntentActivities(MAIN/LAUNCHER)`). The settings are inside a `ScrollView` so they don't clip as they grow. Changing a setting calls the relevant provider's render directly (no refetch). It applies window insets as padding so content clears the status/navigation bars (edge-to-edge is on by default at targetSdk 36).
- `Settings` — app-wide preferences (SharedPreferences-backed): `showCondition`, `unitMode` (`UnitMode.AUTO`/`CELSIUS`/`FAHRENHEIT`), `fontSize` (sp; condition line scales by `CONDITION_SIZE_RATIO`), `dynamicColor`, `textAlign` (`TextAlign.START`/`CENTER`/`END`), and separate launch-package/label prefs for the weather widget (`launchPackage`) and alarm widget (`alarmLaunchPackage`). `resolvedUnit(context)` maps the mode to a `TemperatureUnit`, using the resource-config locale for AUTO. Enum prefs go through `enumPref`/`setEnumPref` (stored by name, unknown value → default).

## Conventions & gotchas

- **Widget layouts use `RemoteViews`** (`res/layout/widget_weather.xml`, `widget_alarm.xml`): only RemoteViews-supported views — `LinearLayout`/`TextView`/`ImageView`, **no `ConstraintLayout`**. The Hack font is referenced statically via `android:fontFamily="@font/hack"` (works in RemoteViews); text color and size are set per-render (`setTextColor`/`setTextViewTextSize`), and a dark shadow (baked in the layout, can't be set via RemoteViews) keeps text legible on any wallpaper. The alarm widget's icon is tinted to match via `setInt(R.id.alarm_icon, "setColorFilter", color)` and sized to the font via `setViewLayoutWidth/Height` (API 31+).
- **Dynamic color lives in `WidgetStyle.textColor`** (not the providers): it uses the Material You **accent** palette (`@android:color/system_accent1_*`, API 31+) — wallpaper-derived but contrast-picked (dark tone for light wallpapers via `WallpaperColors` `HINT_SUPPORTS_DARK_TEXT`, light tone otherwise); pre-31 falls back to black/white by wallpaper luminance. Do **not** use `getWallpaperColors().primaryColor` for text — it's the raw dominant color and blends into the wallpaper. Recomputed each render, so wallpaper changes appear on the next refresh.
- **Text alignment** comes from `WidgetStyle.gravity` and is applied by setting the root `LinearLayout`'s gravity via `views.setInt(R.id.widget_root, "setGravity", gravity)` (`LinearLayout.setGravity` is remotable) — the text views stay `wrap_content`, so the gravity positions them left/center/right.
- **Refresh/heartbeat broadcasts are *explicit* intents** to the provider component (`WeatherWidgetProvider.ACTION_REFRESH`, `ACTION_HEARTBEAT`), so they are delivered without `<action>` entries in the manifest intent-filter — do not re-add them; the constants are the single source of truth. The weather receiver is `exported="true"` (not for these — they're explicit — but) so the system can deliver `BOOT_COMPLETED`, which *is* an `<action>` in the filter and re-arms the heartbeat after a reboot.
- **The tap `PendingIntent` is set on the text views only** (`R.id.temperature`/`R.id.condition`), not the root, so the transparent cell area isn't a tap target. It's either the refresh broadcast or a launch-activity intent for `Settings.launchPackage` (falls back to refresh if the app is uninstalled). Listing/launching installed apps requires the `<queries>` MAIN/LAUNCHER element in the manifest (Android 11+ package visibility) — no `QUERY_ALL_PACKAGES`.
- New persisted state goes through a small SharedPreferences wrapper (`WeatherCache`, `Settings`), not raw key access scattered around.
- New display strings go in `res/values/strings.xml`.
- **App launcher icon** is an adaptive icon: foreground `@mipmap/ic_launcher_fg` (the design scaled to ~76% so it clears circle masks) over `@drawable/ic_launcher_background` (the `#F4E9FC`→`#C8B0FB` gradient). The source master is `icon.png` at the repo root (a squircle on black). To regenerate: de-black it (`magick icon.png -fuzz 8% -transparent black`), composite the cutout centered+scaled over the gradient, and emit `ic_launcher_fg` (108–432 px) + legacy `ic_launcher`/`ic_launcher_round` (48–192 px). Widget *picker* icons are separate: `ic_launcher_foreground` (sun) for Weather, `ic_alarm` for Alarm.
